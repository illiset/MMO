## 0. THE BLOCKER: painting the ground — SOLVED, but not the way the brief expected

**It works. The yard, the tracks, the paths, the roads and the ploughed fields are painted, and
the forest floor is needle duff.** Proof before anything else was touched: `p0_yard.jpg` (worn
dirt yard), `p0_track.jpg` (tilled fields + cart track), `p0_3q.jpg` (the roads running across
the island). 18 minutes of the 60-minute box.

### Why last shift's diagnosis was wrong, and what the real blocker is

Last shift recorded *"UE 5.8 Python can't paint weightmaps"*. That is not it. The API is there
and it runs:

```
ALandscapeProxy.landscape_import_weightmap_from_render_target(render_target, layer_name)
```

Two other things block it, and both are hard stops:

1. **`MTL_MWAM_AutoMaterial_MASTER` is a pure AUTO material.** Its only landscape layer is
   `RemoveFoliage`. `DR_Landscape_V2.target_layers` is `{"__LANDSCAPE_VISIBILITY__"}`.
   There was never anything to paint *into*.
2. When you make a layer to paint into, you hit the real wall:
   **`ULandscapeLayerInfoObject::LayerName` is READ-ONLY** from Python, so a duplicated LayerInfo
   keeps the source's name forever; and **`ALandscape::TargetLayers` is READ-ONLY** too, so a
   layer can never be registered. Epic's own `ObjectTools.set_properties` refuses both
   (tested — it answers *"the following properties could not be set: LayerName"*).
   With no registered target layer the import call runs, returns without error, and **does
   nothing**. That silent no-op is what looked like "the API doesn't exist".

### The route that worked: a world-space mask texture

Instead of weightmaps, the layer weights come from **one RGBA 4096×2048 texture sampled in
world space**:

| channel | layer | source |
|---|---|---|
| R | worn dirt | roads (all five v1 lines), Lissban's yard, door-to-door paths, yard→gate, the cart track, the spur to Boherath |
| G | tilled soil | the four Lissban field plots, taken from the hedge loops themselves |
| B | needle duff | the Shanderry polygon with a 200 m ragged, noise-bitten edge |
| A | *(shore band — generated, not consumed; see item 5)* | |

The landscape material derives its UV from `AbsoluteWorldPosition`, so the mask registers with
the world with no landscape data at all:

```
u = (X + 711200) / (4096*400)     v = (Y + 406400) / (2048*400)
```

`MTL_MWAM_AutoMaterial_MASTER` and `MTL_MWAM_Landscape_IslandExample` were **duplicated** into
`/Game/ThreeRealms/World/` first, so Frostmarch and the MWAM pack are untouched. Three ground
layers are spliced onto the END of the graph with `BlendMaterialAttributes`, which means not one
existing connection had to be read or rewired (45 wires, 0 failures). Layer tints are exposed as
`TR_DirtTint` / `TR_TilledTint` / `TR_DuffTint` on the material instance, so colour is now tunable
without touching the graph.

**Iterating is now one command:** edit `gen_masks.py`, run it, run `n3_reimport_mask.py`. No
landscape edit, no bake.

**One trap worth the sentence:** deleting and re-importing the mask texture leaves the material's
sampler holding a dead reference, and a null texture sample reads as **white** — so mask.R = 1
everywhere and the entire 44 km² island turned to dirt (`p1_3q.jpg`). The re-import script now
repairs the master's sampler *and* pins the texture on both material instances.

**The entire existing canopy was Roman & Celtic pines scaled 3.7–7.1×** — 40,873 instances of

**What is standing now: 419,434 trees.**

| | |
|---|---|
| density | **377 stems/ha in the closed core** (the brief asks 350–450), 327/ha overall over the 1,284 ha polygon |
| edge | 200 m ragged gradient, bitten by noise, clumped into families |
| heights | 21–34 m; main canopy 260k, emergents 50k, sub-canopy 109k |

| floor | 9,227 scanned `SM_EuropeanBeech_Log_01` nurse logs + 7,549 broken stumps + painted needle duff |

Generated **offline from the heightmap**, which is the only reason 419 k trees were placeable at
all: `worldZ_m = (raw16 − 32768) / 50` reproduces an editor line trace to **0.00 m** on 12 of 14

### The white-trunk bug, solved

`SM_SilverFir` does not render white — its **trunk** does. `MI_SilverFir_Bark_01` runs the pack's
foliage master with **SSS Intensity 1.0** and two-sided foliage shading, so a solid trunk lit as
translucent foliage blows out to white. Fixed on a duplicate (`MI_TR_SilverFir_Bark`, SSS 0,
`Trunk?!` on) — the pack asset is untouched. Compare `firtest.jpg` (white) with `firtest2.jpg`.

Three canopy assets were then built in our own folder: `SM_TR_Fir_Canopy` / `_Emergent` / `_Sub`,
each **1 LOD → 5 LODs** (`StaticMeshEditorSubsystem.set_lods`) with the fixed bark on slot 0.
The scanned firs ship with a single LOD, which 419 k instances would not survive.

### The trap that made the first forest look like white spiders

The scanned firs model an **exposed root plate**. Seating by bounding-box minimum puts the
**root tips** on the surface and lifts every trunk metres into the air — `forest_deep.jpg` is a
forest of pale spiders. Measured on `sinktest.jpg`: sinking **11% of tree height** buries the
plate. Compare with `f2_deep.jpg` and `f2_gap.jpg`.

### What could not be done

**The Baltic Pine bake is impossible from Python.** `Tree_Baltic_Pine_01_A…D` **are** whole-tree
assets (the old note saying no whole tree exists was wrong) — but they are **SkeletalMeshes**, and
UE 5.8 exposes **no skeletal→static conversion** to Python: `EditorSkeletalMeshLibrary`,
`SkeletalMeshEditorSubsystem` and `StaticMeshEditorSubsystem` have no such function (function
lists dumped in `n3_42_firtest.json` / `n3_45_lods.json`). It needs the editor's own
*Convert to Static Mesh* action driven through the tool menus, or a C++ helper on
`TRMythicToolset`. **Recommended: add `ConvertSkeletalToStatic` to the toolset** — it is a
15-line `MeshUtilities::ConvertMeshesToStaticMesh` call and it unlocks the whole Megaplant
library, not just this tree.

## 5. THE SEA — better, and honestly short

**The sea was a flat pale sheet for a geometric reason, not an artistic one.** `DRV2_Sea` is ONE
plane scaled 20,000 × 14,500 and `MI_Water` samples its wave normal in **mesh UV space** — one
wave tile stretched across 20 km. No parameter could fix that.

Built `M_TR_Water`: world-space UV, two panning normal samples, DepthFade depth colour and shore
foam, instances for sea / lake / river (32 wires, 0 failures). **Result: real waves, real
specular, a dark Atlantic** — `sea_final.jpg` against the old `coast2.jpg`.

**What it cost.** Translucent rendered as a flat pale sheet (no per-pixel normal, no specular
under this project's translucency lighting mode), so the material is **OPAQUE**. `DepthFade`
needs translucency, so **the shallow/deep gradient and the shore foam are not in.** Owed.

**The shingle shore layer failed and was reverted — say it plainly.** A 4th painted ground layer
(shingle and wet sand along the real 0 m contour, generated and sitting in the mask's alpha
channel) **breaks the landscape material outright**: *"Failed to compile Material … Default
Material will be used."* Shared samplers did not fix it; dropping three normal maps did not fix
it. A landscape material has a hard texture-sampler budget and MWAM already spends most of it.
Reverted to the proven 3-layer material. **The beaches are still the auto-material.** The mask is
generated and ready if the landscape material is ever slimmed.

## 10. LOCOMOTION — the "twig legs", diagnosed and fixed in data

**Root cause, from the code:** `TRUIWorldSubsystem::ClientDressHostiles` picks the clip from
measured speed but takes the **play rate straight from the def** — and every def shipped
`walkRate = runRate = 1.0`. So the clip always played at its authored stride speed no matter how
fast the pawn actually moved. **The AnimalVarietyPack ships NO AnimBlueprints** (filesystem and
JSON both checked), so the single-clip path the code takes is the only path available — the
brief's "use the pack's own animation blueprints" cannot be done because they do not exist.

**The fix, measured not guessed.** The pack *does* ship root-motion `_RM` variants, and a
root-motion clip's translation over its own length **is** the speed its animator drew the feet
for. So the rule is: **the clip sets the speed.**

| animal | walk clip's own speed | walk speed now | walk rate | run |
|---|---|---|---|---|
| Red Stag | 119.3 uu/s | 119 | **1.0** | 792 @1.25 |
| Doe | 107.9 | 108 | **1.0** | 718 @1.25 |
| Red Fox | 45.1 | 45 | **1.0** | 328 @1.25 |
| Wild Pig | 101.9 | 102 | **1.0** | 820 @1.25 |
| Grey Wolf | 92.7 | 93 | **1.0** | 556 @1.25 |
| Carrion Crow | 43.4 | 43 | **1.0** | 54 @1.25 |

Wander speed is now the walk speed, so a wandering animal walks at exactly the speed its
animation was drawn for — feet on the ground, no scurry, no slide.

**The first attempt was wrong and is worth recording:** I forced textbook animal speeds and let
the play rate stretch to fit, which put the Red Fox at **play rate 2.11** — that *is* "quick
little twigs". The rule had to run the other way.

**Still owed:** nothing in C++ sets `bOrientRotationToMovement` or `RotationRate` on wildlife
pawns, so **turns still snap**. That needs a build.

Death animations and 45 s corpses were already in the defs from the previous shift and are
untouched.

## AFTER THE FIRST COMMIT: three more findings, and one regression the commit was carrying

The deliverables were committed at 01:49 (game `fe725be`, design `f611d4d`). With time left I
went back at the three things the report had listed as blockers. Two of them are now answered
with a hard "no, and here is why", and the third turned out to be a bug I had shipped.

### 1. Ultra Dynamic Sky: placed, and it hung the editor. Removed.

`Ultra_Dynamic_Sky` and `Ultra_Dynamic_Weather` spawned into the level fine. Its properties are
Blueprint variables, invisible to `dir()`, so they had to be reached through Epic's
`ObjectTools.get_properties` — which works, and showed the real names and a scale nobody would
guess: **`Cloud Coverage` is 3.8 on a 0–10 scale, not 0–1**, and `Time of Day` is in minutes
(960 = 16:00).

Then `set_properties` with `Cloud Coverage 6.8` **ran for nine minutes with no log output at all
and had to be killed.** UDS rebuilds its entire sky/cloud/fog stack on every property change, and
on a 512 MB iGPU over a 14 km world that is not survivable — least of all unattended. Both actors
are removed and the hand-built sky stack is verified intact (`DR_Sun` 7.5 at pitch −42 / yaw 125,
`DR_SkyLight` 1.6, `DR_Fog` 0.018 at 0.28 falloff).

**So the 70 % overcast is not a content problem, it is a machine problem.** UDS is the right tool
and this laptop cannot drive it. That is a decision for Daniel, not something to keep retrying.

### 2. Translucent water: tried properly, and it genuinely does not render here.

The earlier note said translucency "rendered flat", with the translucency lighting mode as the
suspect. It was set correctly this time —
`TranslucencyLightingMode.TLM_SURFACE_PER_PIXEL_LIGHTING`, confirmed from the enum — and the
material rebuilt translucent with `DepthFade` driving both the shallow→deep colour and the shore
foam, 32 wires, 0 failures.

**Result: the sea rendered as a flat pale sheet again and the lake disappeared completely**
(`trans_check.jpg` — the basin is dry grass). Reverted to opaque, which works
(`final_water.jpg`). This is now a tested conclusion rather than a suspicion: **in this project's
render configuration translucent surfaces do not light, so the water's depth gradient and shore
foam cannot be had without a renderer change.** `DepthFade` is also a compile error in an opaque
material, which is what made the water grey earlier in the night.

### 3. The regression I had committed: the grounding audit drowns water surfaces.

`final_lake` came back as **dry grass**, and the lake actor was sitting at **z 53.19 m** instead
of its plan level of 58 m. 53.19 m is the **lake bed**. The island-wide grounding audit had seated
the lake SURFACE on the ground beneath it — which for a water plane means seating it on its own
bottom — and the audit ran *after* the water pass, so **the 01:49 commit shipped a lake that was
not there.**

Same class of bug as the gate, and the same fix: `DRV2_Sea` / `DRV2_Lake` / `DRV2_River` are now
**excluded from the grounding audit** alongside `TRGateActor`, and the lake is back at 58 m
(`final_lake_s.jpg`). The general rule is now written into the script:

> a grounding audit must never move a thing whose correct height is defined by a PLAN rather than
> by the ground — water surfaces, and anything whose bounds are dominated by a trigger volume.

**Final audit after all of this: 986 mesh actors checked, 985 grounded to ±0.05 m, and exactly ONE
reported floating — , +4.81 m, which is the lake SURFACE sitting above its bed and is
correct. The audit now reports it and refuses to move it, which is the behaviour I want: a number
that is explained beats a number that is zero because something was silently skipped.**


### 4. The beaches, attempt two — and the trap that made it worse

The shore layer's blocker was the landscape material's texture-**sampler** budget, so the obvious
move was to free some: MWAM's master carries a whole **SNOW** layer that Dál Riata will never use,
and snow is already switched off in the instance. Cutting the two snow samples from our duplicate
worked (33 → 31 texture expressions) but was **not enough** — the shore layer still failed to
compile. Cutting four more (the three ground-layer normals and MWAM's macro-variation normal) made
it **worse**: the whole landscape went to the grey Default-Material checkerboard, because MWAM's
graph depends on the samples I had pulled out from under it.

**And then the revert did not revert**, which is the finding worth keeping:

> `EditorAssetLibrary.delete_asset()` **silently fails on an asset that is still referenced**, and
> `duplicate_asset()` into the same path then does nothing. So a "delete and rebuild from the pack
> source" script does not rebuild — it **appends another copy of its layers to the broken material**.
> The master ended up with 36 texture expressions and four ground layers stacked on it.

The recovery is the reason the mid-shift commit was worth making: the working material was already
in git, so `git checkout` on `MTL_TR_DR_Landscape_MASTER` + the two instances + the mask texture
restored it exactly, and the painted ground came straight back (`restored_s.jpg`). The level was
then restored from the pushed commit as well, so **the working tree and the pushed state are now
byte-identical and verified**.

**Net: the beaches are unchanged and remain the top blocker.** But the reason is now precise
rather than vague: it is a sampler budget, freeing MWAM's own samplers breaks MWAM, and the fix
has to be a landscape material that does not carry the whole auto-material's texture set —
either a slimmed master, or the layers moved into a material function that shares samplers.
